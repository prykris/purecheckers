## Authentication and automatic entry

Source inspection found unbounded requests in AuthScreen and automatic invite entry, late nickname suggestions overwriting typing, and obsolete form requests surviving a view change. AuthenticationFlow now owns one mounted form's request lifecycle. It uses the existing 15-second deadline and AccountSession's authentication generation; AccountSession remains the only identity writer. It issues no gameplay command and does not set URLs or screens.

- Guest, login and registration submissions capture their fields and entry source once, prevent duplicate submissions and send no existing bearer token. Switching form or disposing cancels the old request and rejects late results even when cancellation is ignored. Another authentication/account generation also supersedes the response.
- Failed or timed-out requests release the loading state. Registration timeout directs the player to sign in with the same credentials because account creation may have succeeded despite a lost response; no automatic registration retry is issued.
- Suggested guest names are optional and cannot replace typing, appear on another form, or apply after submission/disposal. Form controls have accessible names, errors are announced and loading buttons name the operation.
- AppBootstrap bounds profile restoration, invite lookup and automatic guest creation. Its existing token/generation/invite checks still prevent obsolete entry. Expired credentials can resume a valid invite; network failure retains saved credentials. Failed automatic guest entry returns to manual authentication without joining a room through a second path.

Tests use the real AccountSession owner and controlled asynchronous responses. Cases cover duplicates, late success/failure, account changes, view changes, disposal, typing during a suggestion, invalid credentials payloads, deadlines and explicit retry. Bootstrap tests cover each timed-out step and retain the existing expired-invite/auth/navigation cases. ## Session ordering and room admission

The next backend pass found that quick-play pairing bypassed both players' command queues, and reconnect restoration began before the previous command settled. `enqueueSessionWork` now reserves every participating session's queue synchronously. Pairing, commands and restoration use that ordering; unrelated sessions remain independent. Gameplay admission captures the lifetime before queuing and drains queued work on shutdown. The queue supplies ordering only: phase, readiness, membership and financial policy stay in the existing domain services.

Room creation carries its existing actor guard into the repository transaction. It checks before a new creation, after account reads/locks and after membership writes, so an obsolete actor causes the complete transaction to roll back. A matching creation receipt remains confirmable after the original connection disappears. A failed restoration cannot dispatch gameplay commands through its incomplete connection.

Socket integration covers human pairing admitted before bot fallback, bot fallback admitted before a captured pair, and replacement connection recovery while old room creation is paused. Transaction tests invalidate the actor during account lookup and after membership writes and verify that neither room nor membership commits. Shared queue tests cover overlapping participants, independent sessions, failures and recovery ordering; shutdown tests cover work still waiting for a session queue.

## Pair ownership and uncertain creation recovery

QuickPlayPool now retains an exact claim on each search while pairing owns it. A claimed entry cannot be matched again. Cancel, disconnect and bot fallback invalidate that claim. Finishing or restoring an old claim cannot remove, revive or modify a newer search, including a newer search already claimed by another pair. Requeue retains the original entry, wait timestamp and FIFO position; it does not reset the session's existing fallback deadline. An unaffected partner continues searching instead of being sent to idle. Replacement connections may retain the same search, but a pair captured on the old connection must release it for a fresh admission attempt.

The existing room-creation boundary now resolves uncertain outcomes for configured rooms, bot rooms and human pairs. After its normal idempotent creation retry, it confirms the creator/request identity under the same database advisory lock used by creation. This read cannot race ahead of an old transaction that is still committing. A committed record is projected; a confirmed missing record reports the original error. Changed creation intent is still rejected. Transient projection failures retry that accepted record rather than create another room.

Unavailable confirmation retains the owning session work and retries with backoff from one to ten seconds. It holds no database lock between attempts. Later gameplay commands stay ordered behind confirmation; the server does not guess that a failed response means a failed write. Runtime shutdown interrupts backoff and drains the admitted work. A sustained storage outage can therefore keep affected commands pending until storage recovers or the runtime stops; there is no timeout that silently requeues an unknown committed membership. Existing connection recovery/startup restoration still owns reconnect and hard-restart behavior.

Before requeueing a confirmed failed pair, the domain reprojects any existing durable membership. A player found in another accepted room stays there; only a still-connected, still-searching owner of the exact claim returns to the queue. The pair uses the existing participant queues and authoritative room/session projections; no browser queue owner or second room state machine was added.

## Waiting-room projections and screen wake locks

The waiting room previously inferred “Couldn't start” from an ordinary auto-ready WAITING snapshot with two online players. It also marked auto-ready humans Ready regardless of their accepted online state and offered Add Bot in wager rooms even though the server rejects that action.

The server now uses one `isRoomPlayerReady` predicate for start eligibility and projected player readiness. Stored manual ready flags remain intact; the snapshot's `ready` expresses effective readiness, including online presence and auto-ready policy. `readyToStart` and `canAddBot` expose room-level availability only when no room update is pending. The existing host/connection checks still authorize commands; an availability flag is not a permission grant. Bot admission reuses the same free-room/one-seat predicate as its projection.

RoomWaiting renders these fields directly. A startable auto-ready room says “Ready to start” and provides the existing Start game command; actual command rejection remains in the existing error bar. Offline auto-ready humans no longer display Ready. Add Bot appears only for the host when the server says the room allows it. No second readiness graph or client failure heuristic was added, and readiness/start policy itself is unchanged.

ScreenWakeLock now owns the optional browser resource while a waiting host's scannable image is visible, in either nearby or configured rooms. It deduplicates acquisition for the current room, invalidates pending work on hide/room change/disposal, releases late acquired locks and prevents old release events from clearing a newer lock. Visibility return can acquire again. Both synchronous and asynchronous refusal/release failures are contained; this resource issues no gameplay command and cannot block entry.

The [Screen Wake Lock specification](https://www.w3.org/TR/screen-wake-lock/) makes acquisition visibility-dependent and permits the browser to refuse or release a lock. The implementation treats it as optional. The tests use controlled promises and sentinels; they do not establish actual phone/browser power behavior.

## Game-event ownership and recovery

`src/lib/gameAnalytics.js` is a read-only observer attached to the accepted session stream in `socketService.js`. Components no longer report game lifecycle events or leave a global start-source marker before sending commands. Start follows the server's started/terminal state, first move follows the participant's accepted history using the shared game rules, and result classification uses the shared result policy. Spectators do not generate player events. Reporting failures cannot interrupt session recovery.

Deduplication is scoped by participant and game, retained in memory and optionally in sessionStorage for the last 128 games. It survives screen changes, reconnects and same-tab reloads when storage works. Unknown games first encountered after connection/recovery establish a historical baseline; their previous starts, moves and results are not emitted with current timestamps. New evidence for an already known game can emit once with `recovered: true`. Analytics calls are best effort, not an exactly-once delivery guarantee: blocked tags, cleared/denied storage, evicted history and separate tabs remain limits.

Cancellation, account changes and recovery gaps discard uncertain journey attribution. Rematch click events remain separate; start events no longer claim `rematch`/`rematch-bot` from an unconfirmed click. Configured rooms that produce server origin `bot` use `bot`; this taxonomy does not prove all invite-link conversions. The cohort field is implemented by the later GA4 checkpoint below; production delivery/report definitions remain unfinished.

## GA4 first-session cohort and source correction

`analytics.js` now enriches `game_start`, `first_move` and `game_end` with `first_session` from GA4's own positive integer `session_number`: 1 means true, later sessions mean false. This is the analytics visitor's session, not an account's first game or first sign-in. The supported lookup is documented in the [Google tag API reference](https://developers.google.com/tag-platform/gtagjs/reference#get); [Google's session definition](https://support.google.com/analytics/answer/9191807?hl=en) describes its session identity and numbering. No additional cookies, visitor identifier or local first-visit counter is introduced.

The reporting boundary captures route and event parameters at invocation, coalesces overlapping lookups, preserves event order and waits at most 250ms before emitting with `cohort_status: unknown` and no `first_session`. Valid lookups add `cohort_status: known`. Unknown must not be included as returning visitors in reports. Late/duplicate callbacks cannot repeat events or complete a newer lookup. A batch is limited to 64 events, all reporting exceptions are isolated, and no game action awaits analytics. Each new batch reads the current session number; no permanent cohort cache can outlive the GA session. The script URL in `app.html` is now the sole measurement-ID value used for both configuration and lookup.

Source correction: a server `origin: room` now reports `source: room`, not `invite`. Hosts, room-directory joins and invitation recipients previously shared this origin, so that field never proved link conversion. Older in-tab journals are normalized without replaying completed events. Already delivered historical data is not rewritten. The earlier source taxonomy paragraph is superseded on this point. A true invitation conversion still requires evidence tying link entry to accepted membership/game start, surviving sign-in and reconnects; the plan's invite-conversion metric remains **unverified and unfinished**.

## Request deadlines and cancellation

The shared deadline helper previously only called AbortController.abort and continued awaiting the transport. A loader that ignored cancellation could therefore leave authentication or a read owner pending indefinitely. The prior ReadResource timeout test only used a cooperative fetch double, so it did not prove that the owner itself finished by its deadline.

`actions/deadline.js` now settles its observed promise independently of the transport, while still signalling abort. It accepts the owner's optional signal and a timeout duration (default 15 seconds). It rejects on deadline with the supplied message, ends observation immediately on owner cancellation, never invokes work for an already-aborted owner, and removes its timer/listeners on every terminal path. It observes late transport rejections without allowing a second completion. A newer invocation has its own controller and deadline.

ReadResource, AuthenticationFlow, AppBootstrap and AccountUpgrade now use that same mechanism. Removed their duplicate timeout machinery or composed-signal handling where the owner signal can be passed directly. AccountUpgrade retains its existing same-account /me confirmation before retrying a potentially committed write; no credentials or extra receipt storage are introduced. Other wallet/admin callers retain their existing command/receipt reconciliation through the strengthened shared helper.

A deadline bounds client observation; it is not proof of server rollback, write failure, interrupted CPU work or absence of a later commit. Business owners still resolve uncertain writes through their existing identities and authoritative reads. This is the same server/client authority boundary, not a new business transition.
