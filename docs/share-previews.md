# Sharing and preview images

Results, replay pages, profiles, invitations and puzzle results use `src/lib/share.js` and `ShareActions.svelte`. Native sharing falls back to clipboard; cancellation stays quiet. If both mechanisms are unavailable, a labelled readonly input exposes the actual attributed target URL for manual selection. It never substitutes the current browser address, which is not an invitation on the waiting-room screen. The fallback disappears when its target changes. URLs use `utm_source=share` and the surface as `utm_medium`. Result sharing requires a saved database replay ID. Optional win/milestone prompts are capped per account, surface and UTC date; losses never prompt.

`/og/game/:id.png`, `/og/player/:username.png`, `/og/puzzle/:date.png` and `/og/invite/:code.png` produce 1200×630 PNGs. Values come from stored records or the live room; templates never interpolate URL text. The puzzle renderer never receives a solution, and no card queries chat. Missing, invalid, expired or failed renders redirect to the static card with `no-store`.

`server/og/service.js` centralizes record lookup, coalescing, cache identity and rendering. SVG templates escape text and share the board renderer. Rasterization uses the existing `WorkerPool` class with one separate worker, eight queued jobs and a five-second deadline. It cannot run a native render on the socket event loop. The LRU holds at most 200 images or 16 MiB. Ranked result persistence schedules an optional warm-up without waiting for it.

Game and published puzzle images are immutable. Invitations cache for 60 seconds, but the service checks the live room before using a cached image. Player images require HTTP revalidation; the service rechecks profile visibility before returning an image or 304. Internally, player images can be reused for an hour when their data is unchanged. Third-party social services may retain old public previews independently of our cache.

The profile toggle hides the public profile and profile image, removes its link from discovery, and excludes the profile from newly generated sitemaps. Leaderboard names/rankings and names in opponents' game records remain public. Profile pages return an uncached 404 with the normal noindex error page when hidden.

New games persist an end reason. Older games without one say only that the game ended; the replay no longer invents a forfeiture from the remaining board. Replay and profile pages own fresh component state for each route load.

Local checks cover real PNG signatures/dimensions, ETags, private/expired cached requests, future puzzles, render coalescing/failure recovery, cache limits, XML escaping and actual engine replay. All four sample cards were rendered and visually inspected. A built-adapter HTTP check verified one generated image tag per game, player, puzzle and invite page, and measured one local puzzle-card render at 55 ms. This is not Railway latency or external social-preview validation.

Before deploying, retain optional dependencies and the Poppins fonts under `src/static/fonts`. The lockfile contains both Linux x64 GNU and musl resvg packages; the actual Railway target still needs deployment verification. Check sharing on the owner's phone and external card validators after deployment. No external posts were sent.

## Share contract audit, 11 September 2026

Result messages now use the participant's perspective, recorded history length and a confirmed positive ranked ELO change. Replays use third-person color results; cancellations and unknown results stay neutral. Own-profile messages include ELO/W/L and first-person wording, while public profile sharing names the profile owner without claiming it belongs to the visitor. Puzzle text retains plan 03's spoiler-free solve/try wording (03 owns that UX) and adds plan 06's puzzle-only hashtag. Supported messages are tested below 140 characters with 40-character names. History length means recorded move steps, consistent with the current replay summary; it is not a full red/black move-pair count.

`share` now records each attempted native/clipboard method before invoking it, as plan 06 specifies. `share_cancel` carries the same surface, path and method. A rejected native attempt followed by clipboard counts two attempts, not two successful shares. `invite_link_shared` and `puzzle_share` still come from confirmed UI callbacks. No browser event proves the recipient received a link. Reporting changes require corresponding dashboard interpretation; production GA4 receipt remains unverified. Copied feedback lasts two seconds. Null native rejection values now fall back safely instead of throwing from the error handler.

`shared/previewImages.js` owns the template version used by both renderer cache identity and all four page loaders. This replaces four stale `t=1` strings while the renderer already used version 2. Profile URLs retain their games-played revision, including zero; path identities are encoded. Replay loaders now specify `ogType: article` and include the result in image alternative text. The single-image marketing layout and keyed replay/profile route wrappers were inspected; they already own the correct tag and view lifetime.

The robots dependency now includes both `Disallow: /game$` and `Disallow: /game?`, preserving `Allow: /game/` and crawlable `/join/` previews. This follows the plan's distinction between the app screen and public replay URLs; Google's [path-matching documentation](https://developers.google.com/crawling/docs/robots-txt/robots-txt-spec#url-matching-based-on-path-values) defines terminal `$` matching. The local test checks the shipped directives; it does not prove a crawler refreshed its cache.

## Version 3: content, fitting and centered crops

The original plan simultaneously placed a 534px board at x=48 and required the board and result to survive the central 630px crop (x=285–915). Those coordinates cannot satisfy both requirements. Version 3 prioritizes keeping the board, outcome and essential details together: a 330px board and a 222px detail column sit within the centered square, with names/reason above and date/brand below. The outer asset remains 1200×630. This explicitly supersedes the old absolute layout coordinates rather than claiming that a clipped board satisfies the crop requirement.

Game cards now show named win/draw headlines, the recorded reason, move-step count, side labels/discs, winner emphasis and signed green/red ranked rating chips. Friendly cards omit rating chips. A separate short outcome label remains visible even when exceptionally long names require ellipses. Invitation cards add the host initials disc and reuse one decorative starting-board fragment. Only non-default clocks add a clock line. Wager cards and waiting-room share text state the buy-in and registration requirement; the previous universal “No account needed” claim was incorrect for wagers. Full maximum-sized wager values are retained. Puzzle cards remain spoiler-free and avoid promising a forced game win.

The renderer fits bounded template text using resvg's actual Poppins glyph bounds, reducing only to a declared minimum and then adding a visible grapheme-safe ellipsis. XML entities stay escaped. This runs inside the existing bounded raster worker, not on the socket event loop. Board crown geometry scales with the board; a border keeps its extent clear. The shared preview version is now 3, so loaders advertise the same version used by cache identity.

## Prompt lifecycle and public disclosures

The component's one-time `promptedGame` flag previously retained stale milestone presentation after privacy or eligibility changes. SharePromptView now owns a single surface/reason grant for each participant/game view. Only terminal, saved, qualifying wins can claim it. Repeated snapshots refresh currently eligible content without repeating telemetry; changed profile names update their encoded URLs. Once a grant becomes ineligible, it is revoked rather than transferred to another surface or revived later in that view. Pending persistence does not consume a claim. Ordinary share actions remain available independently of promotion.

Frequency checking now treats either today's memory claim or today's storage value as sufficient suppression. A readable old value can no longer override a current in-memory claim when writing storage fails. Memory retains only the currently checked UTC day. The existing localStorage mechanism is a presentation cap, not an atomic cross-tab transaction; simultaneous tabs and cleared storage are not covered by a claim of globally exactly-once prompting.

The FAQ now has eleven questions: the existing ten, updated for current behavior, plus public-profile/guest/link-preview privacy. Its new answer explains that hiding a profile does not hide leaderboard or saved-game names; guest profile links expire; retired guests appear as Guest; and social apps can retain older previews. Account, coin, friend-room and reconnection wording was corrected. The approved reward constant now lives in `shared/constants.js`, used by both the reward service and FAQ; its value and transaction policy are unchanged.
